## 0. 一句话总览

一次"Agent 深度审计"是一条**由 5 个阶段、4 个智能体 + 1 个确定性前哨串成的流水线**，全程由前端 SSE 事件流实时可视化：

```
HTTP POST /api/v1/agent-tasks/
        │
        ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 0：任务准备（_execute_agent_task）                             │
│  代码落盘 → 沙箱初始化 → RAG 索引 → 实例化 4 Agent                  │
└────────────────────────────────┬────────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 1：Preflight（确定性前哨，非 LLM）                             │
│  osv-scanner + gitleaks + semgrep + OSV 仓库自识别                  │
│  产出 preflight_summary，作为下游 Agent 的"已知情报"                │
└────────────────────────────────┬────────────────────────────────────┘
                                 ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 2：Orchestrator（编排 Agent，ReAct）                           │
│  由 LLM 决定下一步派谁                                              │
└─────┬───────────────┬─────────────────┬────────────────┬────────────┘
      ▼               ▼                 ▼                ▼
   ┌───────┐      ┌──────────┐     ┌────────────┐   ┌──────────────┐
   │ Recon │ ───▶ │ Analysis │ ──▶ │ Refinement │──▶│ Verification │
   │ 侦察  │      │ 分析     │     │ 二次分析   │   │ 沙箱验证 PoC │
   └───────┘      └──────────┘     └────────────┘   └──────────────┘
                                 │
                                 ▼
┌─────────────────────────────────────────────────────────────────────┐
│ 阶段 3：结果落库 + 报告懒生成                                       │
│  _save_findings → task.status=COMPLETED                             │
│  前端拉 GET /report?format=markdown 时才拼报告                      │
└─────────────────────────────────────────────────────────────────────┘
```

- **总控**：`_execute_agent_task`（FastAPI `background_tasks`）
- **大脑**：`OrchestratorAgent`（ReAct，LLM 全程参与决策，`max_iterations=20`）
- **四个子智能体**：Recon / Analysis / Refinement / Verification
- **一个前哨**：`stages/preflight.py`，不含 LLM，跑三大确定性外部工具
- **数据接力棒**：`TaskHandoff` 结构 + `previous_results` 双通道传给下一位

## 1. 阶段 0：任务准备（PLANNING）

**入口**：`backend/app/api/v1/endpoints/agent_tasks.py::create_agent_task`
**HTTP**：`POST /api/v1/agent-tasks/`
**后台执行函数**：`_execute_agent_task(task_id)`（FastAPI `background_tasks.add_task`）
**任务表状态**：`agent_tasks.status = PENDING → RUNNING`，`current_phase = PLANNING`

这个阶段完全是"环境搭建"，还没有任何 Agent 上场：

| 步骤 | 具体动作 | 说明 |
|---|---|---|
| 1) SandboxManager 初始化 | `await sandbox_manager.initialize()` | Docker 沙箱守护起来，后面 Verification 才能起容器跑 PoC |
| 2) EventManager + AgentEventEmitter | 注册到 `_running_event_managers[task_id]` | SSE 事件流的**发射端**，所有阶段的进度、思考、finding 都从这走 |
| 3) 拉用户配置 | `_get_user_config` | 解密 SSH 私钥、GitHub/GitLab/Gitea Token、LLM 配置 |
| 4) 代码落盘 | `_get_project_root(...)` | ZIP 走 `safe_extract_zip` 解到 `/tmp/deepaudit/{task_id}`；Git 仓库走 `subprocess git clone`（带 branch + token） |
| 5) target_files 路径回捞 | 若用户指定的文件因目录下沉失效，自动拼回来 | 保证限定范围扫描不漏 |
| 6) LLMService | 按用户配置造出 LLM 适配器 | DeepSeek / OpenAI / Claude / 豆包 / 文心 / MiniMax |
| 7) **RAG 索引构建** | `CodeIndexer.smart_index_directory(...)` | tree-sitter 分块 → embedding → 向量库。进度通过 emitter 发到 SSE |
| 8) 挂 RAG 工具 | `rag_query / security_search / function_context` 挂到每个子 Agent 的 tools | Agent 从此可以做代码语义搜索 |
| 9) 实例化四 Agent | `ReconAgent / AnalysisAgent / RefinementAgent / VerificationAgent` | 每个都构造 `AgentConfig`、`system_prompt`、`tools` |
| 10) 塞进 Orchestrator | `OrchestratorAgent(sub_agents={"recon": ..., "analysis": ..., "refinement": ..., "verification": ...})` | 编排层持有子 Agent 树 |
| 11) `_collect_project_info` | 汇总项目名、语言、文件数 → 写回 `task.total_files` | 给下游 Agent 的 initial message 用 |

准备完毕后进入下一阶段。

## 2. 阶段 1：Preflight（RECONNAISSANCE，确定性前哨）

**代码位置**：`backend/app/services/agent/stages/preflight.py::run_preflight`
**任务表**：`current_phase = RECONNAISSANCE`
**特征**：**不含任何 LLM 调用**，是一条纯确定性流水线；工具失败降级为 `warnings`，永不阻塞主流程。

### 2.1 为什么要有 Preflight

见 `deepaudit修改文档.md §2`。原始版本让 Recon Agent 自己判断"要不要跑 SCA"，导致 LLM 经常忽略依赖清单里的已知 CVE。Preflight 把这一切从 LLM 决策路径上剥离：**已知的、有权威源的东西先跑确定性工具，把结果打包成 `preflight_summary` 塞给下游 Agent**。

### 2.2 具体扫描步骤

按顺序执行 5 步（每步有独立开关 `enable_sca / enable_secrets / enable_sast`）：

| # | 步骤 | 工具 | 触发条件 |
|---|---|---|---|
| 1 | **Manifest 探测** | 内置 `_find_manifests` | 一层子目录深度扫，匹配 `requirements.txt / pyproject.toml / package.json / go.mod / pom.xml / Cargo.toml / composer.json / Gemfile` 等 |
| 2 | **SCA (依赖漏洞)** | `OSVScannerTool`（osv-scanner） | 仅当 `has_manifest=True` |
| 2.5 | **仓库自识别 (Self-CVE)** | 直连 `https://api.osv.dev/v1/query` | 从 manifest 提 `(name, version, ecosystem)`，防止"仓库自身就是某历史版本 log4j / Flask" 被漏掉；命中后按 id 去重合并进 sca |
| 3 | **Secrets** | `GitleaksTool` | 全量执行 |
| 4 | **SAST** | `SemgrepTool` (`p/security-audit` 规则集) | 只保留前 20 条 |
| 5 | **摘要构建** | `_build_summary_text` | 生成 prompt-friendly 的中文文本，尾部显式提示下游"不要重复调用 osv_scan / gitleaks_scan / semgrep_scan" |

### 2.3 输出结构 `preflight_summary`

```json
{
  "has_manifest": true,
  "manifests": ["backend/requirements.txt", ...],
  "sca":     {"tool": "osv-scanner", "count": N, "vulnerabilities": [{id, ...}]},
  "secrets": {"tool": "gitleaks",    "count": N, "leaks": [...]},
  "sast":    {"tool": "semgrep",     "count": N, "findings": [{check_id, path, line, severity, message}]},
  "self_identity": {"name", "version", "ecosystem", "vulnerabilities": [...]},
  "warnings": [...],
  "summary_text": "Preflight 阶段已经跑完 SCA / Secrets / SAST ..."
}
```

这个字典会以 `input_data["preflight_summary"]` 透传给 Orchestrator 及所有子 Agent。

### 2.4 兜底注入（防漏报保险丝）

`OrchestratorAgent._inject_preflight_findings_if_missing`：如果 Recon Agent 交作业时**一条 `source=sca/secrets/sast` 的 finding 都没写**，说明 LLM 忽视了前置结果，Orchestrator 会自动把 Preflight 的原始条目合成标准 finding 补进 `_all_findings`（SCA 命中默认 severity=high，`is_verified=True`，`confidence=0.95`）。

## 3. 阶段 2：Orchestrator 编排 + 四子 Agent 协作

**代码位置**：`backend/app/services/agent/agents/orchestrator.py::OrchestratorAgent.run`
**任务表**：`current_phase = ANALYSIS`
**模式**：`AgentPattern.REACT`，`max_iterations=20`
**核心理念**：**LLM 是大脑，Orchestrator 每一轮都问 LLM"下一步派谁"**

### 3.1 Orchestrator 的三种 Action

LLM 每轮输出 `Thought / Action / Action Input`，其中 Action 只有三种：

| Action | 语义 | 参数 |
|---|---|---|
| `dispatch_agent` | 把任务派给某个子 Agent | `{"agent": "recon|analysis|refinement|verification", "task": "...", "context": "..."}` |
| `summarize` | 让 Orchestrator 打印当前 findings 汇总 | `{}` |
| `finish` | 判定审计足够充分，结束 | `{"conclusion", "findings", "recommendations"}` |

### 3.2 硬约束（`§4` 落地）

Orchestrator 里写死了一条**流程护栏**（`orchestrator.py` L692-706）：

> 如果 `analysis` 已经跑过、且 `refinement` 还没跑过，就**禁止 dispatch verification**——直接拦下来，把决策掐掉，回一段引导让 LLM 输出 `dispatch_agent {"agent": "refinement"}`。

这一层不是软提示，是真的 `return` 一段错误提示，防止 Agent 在 Analysis 出结果后直接扑向 Verification。

### 3.3 一次典型的编排轨迹

一次成功审计的 Action 序列通常是：

```
Iter 1  Thought: 先了解项目 → Action: dispatch_agent(recon)
Iter 2  Observation: Recon 完成，返回项目结构/tech_stack/high_risk_areas
Iter 3  Thought: 高风险区域清楚了 → Action: dispatch_agent(analysis)
Iter 4  Observation: Analysis 完成，返回 N 个 findings（含低置信度）
Iter 5  Thought: 有低置信度 finding，先精修 → Action: dispatch_agent(refinement)
Iter 6  Observation: Refinement 完成：保留 X，丢弃 Y，待人工 Z
Iter 7  Thought: 剩下的送验证 → Action: dispatch_agent(verification)
Iter 8  Observation: Verification 完成，附带 PoC 与 ASAN 日志
Iter 9  Thought: 审计充分 → Action: finish
```

### 3.4 数据接力（TaskHandoff）

每个子 Agent 跑完都会返回一份 `TaskHandoff`（`agents/base.py::TaskHandoff`），Orchestrator 会**根据下一个目标 Agent 自动挑一份 handoff 传过去**（`_build_handoff_for_agent`）：

| 目标 Agent | 拿到的 handoff | 关键字段 |
|---|---|---|
| Analysis | Recon 的 handoff | `key_findings`（Recon 初步发现）、`priority_areas`（高风险区域）、`attention_points`（入口点） |
| Refinement | Analysis 的 handoff | `key_findings = Analysis 全部 findings`（自行分桶） |
| Verification | Refinement 的 handoff（优先），退化到 Analysis 的 | `key_findings`（refined_confirmed + passthrough）、`suggested_actions`（verify 目标） |

除了 handoff，Orchestrator 还把之前所有 Agent 的完整 `AgentResult.data` 打包到 `previous_results` 里一并传下去，作为回退路径。

## 4. 四个子智能体详解

四个子 Agent 都继承自 `agents/base.py::BaseAgent`，共享 ReAct 循环、事件发射、工具调度、Handoff 机制。下面按**流水线顺序**逐个讲。

### 4.1 Recon Agent（侦察 / 信息收集）

**代码位置**：`backend/app/services/agent/agents/recon.py`
**类型**：`AgentType.RECON`，`AgentPattern.REACT`，`max_iterations=15`
**定位**：侦察层，为下游铺路，不做深入漏洞判定。

#### 4.1.1 目标

- 识别技术栈（语言 / 框架 / 数据库 / 前端）
- 找入口点（HTTP 路由、WebSocket、定时任务、消息队列）
- 定位敏感/高风险区域（认证 / DB / 文件处理 / 外部服务调用）
- 根据技术栈推荐下游要用的工具（`must_use[]` / `recommended[]`）
- **消费 Preflight 结果**，把 SCA / Secrets / SAST 命中转成 `initial_findings`

#### 4.1.2 使用的工具

Prompt 里明确允许调用的：
- `list_files` —— 看根目录结构
- `read_file` —— 读具体文件
- `search_code` —— 关键代码定位
- `rag_query` —— 语义搜索入口点

**明确禁止**：`osv_scan / gitleaks_scan / semgrep_scan`（Preflight 跑过，不再重复烧钱）。
**硬约束**：至少调用 3 个工具，禁止直接 Final Answer；连续 3 次同一失败调用会注入换策略提示。

#### 4.1.3 输出结构

```json
{
  "project_structure": {"directories": [...], "key_files": [...]},
  "tech_stack": {"languages": [...], "frameworks": [...], "databases": [...]},
  "recommended_tools": {"must_use": [...], "recommended": [...], "reason": "..."},
  "entry_points": [{"type", "file", "line", "method"}],
  "high_risk_areas": ["src/xx.py:36 - 描述", ...],
  "initial_findings": [
    {"title", "file_path", "line_start", "description",
     "source": "sca | secrets | sast | recon"}
  ],
  "dependencies": [...],
  "summary": "..."
}
```

同时通过 `_create_recon_handoff` 生成给 Analysis 的 `TaskHandoff`。

### 4.2 Analysis Agent（漏洞分析核心大脑）

**代码位置**：`backend/app/services/agent/agents/analysis.py`
**类型**：`AgentType.ANALYSIS`，`AgentPattern.REACT`，`max_iterations=30`
**定位**：真·安全专家。**不是工具执行器**，而是自主制定策略、选择工具、深入判断的 LLM Agent。

#### 4.2.1 目标

拿着 Recon 的 handoff（tech_stack、entry_points、high_risk_areas、initial_findings），**自主决定**：读哪些文件、跑哪些扫描器、追哪条污点链，最终输出**带证据的 findings**。

#### 4.2.2 使用的工具（分档）

| 优先级 | 工具 | 说明 |
|---|---|---|
| 第一档：外部专业工具 | `semgrep_scan / bandit_scan / gitleaks_scan / safety_scan / npm_audit / kunlun_scan` | 走 sandbox 起容器跑 |
| 第二档：智能扫描 | `smart_scan / quick_audit` | DeepAudit 内置组合拳，减少 LLM 轮数 |
| 第三档：内置分析 | `pattern_match`（危险模式正则） / `dataflow_analysis` | 内置 pattern_tool 派生 |
| RAG & 代码浏览 | `rag_query / security_search / read_file / list_files / search_code` | 走 rag_tool + file_tool |
| 知识 | `get_vulnerability_knowledge / query_security_knowledge` | 走 knowledge/ 里的漏洞与框架知识库 |

#### 4.2.3 finding 结构（标准化后）

```json
{
  "vulnerability_type": "sql_injection",
  "severity": "critical | high | medium | low",
  "title": "...",
  "description": "...",
  "file_path": "app/api/v1/users.py",
  "line_start": 42,
  "code_snippet": "5–30 行真实代码",
  "source": "recon | analysis | sca | secrets | sast",
  "sink": "...",
  "suggestion": "...",
  "confidence": 0.7,
  "needs_verification": true,
  "call_path": ["entry → sink 的调用链"],
  "taint_flow": "污点传播路径",
  "cwe_id": "CWE-89",
  "references": [...]
}
```

#### 4.2.4 上报路径

Analysis 没有名为 `report_vulnerability` 的显式工具调用，实际路径是：
1. LLM 在 `Final Answer` JSON 里返回 `findings[]`
2. `_parse_llm_response` 解析
3. 对前 5 条调 `emit_finding(...)` 事件（前端 SSE 能看到"发现漏洞"卡片弹出）
4. 通过 `handoff.key_findings / suggested_actions` 传给下一个 Agent

### 4.3 Refinement Agent（低置信度二次分析）

**代码位置**：`backend/app/services/agent/agents/refinement.py`
**类型**：`AgentType.ANALYSIS`（复用类型让 UI 视觉一致），`AgentPattern.PLAN_AND_EXECUTE`，`max_iterations=1`
**引入原因**：见 `deepaudit修改文档.md §4`

#### 4.3.1 目标

Analysis Agent 常常吐出**大量低置信度的一句话 finding**（只有描述、没 code_snippet、没 taint_flow）。如果直接送 Verification，Verification 会因为信息不足而摆烂或者盲目跑失败的 PoC。Refinement 就是这中间的"过滤器 + 升格器"。

**关键设计约束**：
- **不跑 ReAct 循环**——每条 finding 只花 1 次 LLM 调用
- **不允许 LLM 决定要不要读文件**——由代码确定性预取上下文
- **不生成新 finding**——只对现有 finding 做保留 / 丢弃 / 挂起

#### 4.3.2 分桶策略

`_bucketize()` 按 `confidence` 与 `source` 把 Analysis 的 findings 分四桶：

| 桶 | 条件 | 处理 |
|---|---|---|
| **high**（passthrough） | `source ∈ {sca, secrets}` 或 `is_verified=True` 或 `confidence ≥ 0.8` | **直接放行**给 Verification，跳过 LLM |
| **mid**（refine） | `0.5 ≤ confidence < 0.8` | 走精修流程 |
| **low**（自动丢） | `confidence < 0.5` | 归入 `dropped_findings`，不入 Verification |

#### 4.3.3 精修流程 `_refine_one`

对 mid 桶每条 finding：
1. `_deterministic_read` 用 `read_file` 抓 `[line-30, line+30]` 上下文
2. `_extract_sink_hint` 从 `sink / vulnerability_type / 描述` 里抽 sink 名字，命中则 `search_code` 取头几行辅证
3. 一次性 LLM 判决（`stream_llm_call`），强制输出 JSON `{verdict, new_confidence, ...}`
4. `_parse_verdict` 强制 verdict 与新 confidence 一致：
   - `confirmed` → `new_conf ≥ 0.75`（低于则拉到 0.8）
   - `false_positive` → `new_conf ≤ 0.3`
   - `still_unclear` → 夹到 `[0.35, 0.7]`
5. 归并回原 finding：
   - `confirmed` → **refined**，加入 `findings`（送 Verification）
   - `false_positive` → **dropped**
   - `still_unclear` 或异常 → **unclear**（进报告"待人工确认"分区）

#### 4.3.4 输出结构

```json
{
  "findings": [/* passthrough + refined_confirmed，送 Verification */],
  "dropped_findings": [/* 低置信度自动丢 + LLM 判 false_positive */],
  "unclear_findings": [/* still_unclear，进报告独立分区 */],
  "refinement_details": {
    "passthrough": [...],
    "refined_confirmed": [...]
  },
  "summary": "Refinement 完成: passthrough=A, refined_confirmed=B, dropped=C, unclear=D"
}
```

Orchestrator 拿到后会**用 Refinement 输出完全替换 `_all_findings`**（不是合并，参见 `orchestrator.py` L869-897）：只保留 refinement 认可的活跃发现集合，`dropped` / `unclear` 单独存到 `_dropped_findings` / `_unclear_findings`，供报告端渲染独立分区。

### 4.4 Verification Agent（沙箱验证 + PoC 生成）

**代码位置**：`backend/app/services/agent/agents/verification.py`
**类型**：`AgentType.VERIFICATION`，`AgentPattern.REACT`，`max_iterations=25`
**核心理念**：**Fuzzing Harness** —— 即使项目跑不起来，也要通过"提函数 + Mock 依赖 + 起沙箱"手写测试脚本来验证。

#### 4.4.1 目标

对 Refinement 放行的 findings 做**动态验证**：

- 判定真伪（confirmed / likely / uncertain / false_positive）
- 生成**可运行的 PoC**（命令 + 输入 + 输出）
- 给出完整证据链（call_path + taint_flow + CWE + 沙箱命令输出）

#### 4.4.2 使用的工具

| 类别 | 工具 | 说明 |
|---|---|---|
| 通用执行 | `run_code` | 多语言：Python / PHP / JS / Ruby / Go / Java / Bash |
| 代码提取 | `extract_function`、`read_file` | 从项目里抠出目标函数做隔离测试 |
| 沙箱通用 | `sandbox_exec`、`sandbox_http` | 起 Docker 沙箱跑命令 / 发 HTTP |
| **C/C++ 动态验证**（§3 改进） | `c_test`、`cpp_test`（gcc/g++ + AddressSanitizer），`fuzz_test`（libFuzzer + ASAN，30–120s） | ASAN 报告被视为"最有力的证据链"；`c_test` 支持 `mode="snippet"` 单文件 PoC 与 `mode="project"` 完整构建（默认 `make`） |

#### 4.4.3 输入优先级

Verification 从 `input_data` 里按优先级找待验证 findings：
1. `handoff.key_findings`（Refinement/Analysis 的接力棒）
2. `previous_results["findings"]`（Orchestrator 汇总）
3. 传统嵌套 `previous_results[phase_name].data.findings`

过滤条件：`needs_verification=True` **或** `severity ∈ {critical, high}`（高危强制验证），
去重后取前 20 条。

> **注**：这是 Verification Agent 自身的输入过滤（哪些 finding 送进沙箱跑 PoC）。
> Orchestrator 的 §7 交叉复核层另有一套范围控制（见 orchestrator.py `_select_cross_review_targets`）：
> - HIGH/CRITICAL → 双盲 A+B 交叉复核
> - MEDIUM       → 单侧 A 验证（2026-07 补充，避免证据链空白）

#### 4.4.4  §7 双盲验证：A（动态沙箱）vs B（静态复核）

Orchestrator 拦截 LLM 对 `verification` 的调度后，不走普通的 Verification Agent，而是内部 fan-out 到两个**独立的 VerificationAgent 实例**（`verification_a` / `verification_b`），用 `mode` 参数限制工具集和行为，实现真正的双盲：

##### A 侧 — 动态沙箱验证（`mode="dynamic"`）

| 维度 | 内容 |
|------|------|
| Prompt 原则 | **"必须把代码拉出来跑一趟才能下结论"** —— 拒绝仅凭读代码就判 verified。即使项目跑不起来，也要提函数 + mock 依赖 + 手动构造输入触发。 |
| 可用工具 | `run_code`（多语言）、`sandbox_exec`、`sandbox_http`、`c_test`、`cpp_test`（gcc/g++ + ASAN）、`fuzz_test`（libFuzzer + ASAN, 30–120s）。辅以 `extract_function` / `read_file` 组装 payload，但不允许仅靠读代码下结论。 |
| 硬证据判定 | `evidence_kind ∈ {sandbox_run, asan_report, fuzz_crash}`，或 `verification_result` 同时包含 `command` + `output` |
| 典型输出 | 沙箱命令执行日志、ASAN crash 报告、PoC 触发截图描述 |

##### B 侧 — 静态代码复核（`mode="static"`）

| 维度 | 内容 |
|------|------|
| Prompt 原则 | **"只看代码本身能不能证伪"** —— 从源码语义出发，寻找净化逻辑、硬编码约束、或调用链阻断的证据。禁用一切沙箱工具。 |
| 可用工具 | `read_file`、`search_code`、`extract_function`、`rag_query`、`security_search` |
| 硬证据判定 | `evidence_kind ∈ {sanitizer_found, source_constrained, taint_path}`，或输出了 `taint_flow` 字段 |
| 典型输出 | "在 sink 前找到了 `htmlspecialchars()` 转义 → 不可利用"、"用户输入被白名单限定在 3 个值内" |

##### 双盲流程

```
Orchestrator 收到 LLM 调度 verification
        │
        ▼
  _select_cross_review_targets()
  筛选 _all_findings 按严重度
        │
        ├── HIGH/CRITICAL → A(动态) + B(静态) 并行运行
        │                   双方互相不可见，各自输出 verdict
        │                   ↓
        │                   _arbitrate() 规则表合成终裁
        │                   verified_high_confidence / conflict / false_positive
        │
        └── MEDIUM → 仅跑 A(动态)，单侧验证
                      降低开销，避免证据链空白
                      裁决：verified_single / false_positive / unverified
```

**裁决规则表**（`_arbitrate`）：纯确定性规则，不调 LLM：

| A 判 | B 判 | 终裁 | 含义 |
|------|------|------|------|
| verified | verified | `verified_high_confidence` | 双盲双确认，至少一方硬证据 |
| verified | rejected | 看硬证据 | 有硬证据一方胜 → `verified_single` 或 `false_positive`；证据相当 → `conflict` 待人工 |
| verified | abstain | `verified_single` | 单侧通过 |
| rejected | rejected | `false_positive` | 双盲双否决，归入误报 |
| 其它 | | `unverified` | 无法完成验证 |

#### 4.4.5 循环护栏

- 完全相同 `(action, action_input)` 出现超过 3 次 → 强制换参数/换工具/输出 uncertain
- 同一调用连续失败 3 次 → 提示换参数或跳过
- **Final Answer 硬门槛**：`_tool_calls > 0` 才允许结束——即"你必须至少跑过一个工具才准盖章"
- Prompt 里硬规定：**不允许输出"无法构造有效的 PoC"**，只允许"已尝试 `c_test / fuzz_test` 但未触发"并附完整日志

#### 4.4.6 输出（finding 补齐字段）

Verification 不新增 finding，而是**在原 finding 上补齐**：

```json
{
  "verdict": "confirmed | likely | uncertain | false_positive",
  "is_verified": true,           // verdict=confirmed，或 (likely 且 confidence>=0.8)
  "confidence": 0.0 - 1.0,
  "verification_method": "...",
  "verification_details": "...",
  "verification_result": {"command", "output", "exit_code"},
  "call_path": [...],
  "taint_flow": "...",
  "poc": {"description", "steps", "payload", "harness_code"},
  "impact": "...",
  "recommendation": "...",
  "cwe_id": "CWE-xxx",
  "verified_at": "2026-07-09T..."
}
```

若 LLM 返回空 findings 而输入非空，代码会兜底把原始 findings 全部标 `uncertain, confidence=0.5` 回传。

## 5. 阶段 3：结果落库 + 报告懒生成（REPORTING）

**代码位置**：`_execute_agent_task` L570-660 + `generate_audit_report` L3368

`orchestrator.run(input_data)` 返回后：

1. **`_save_findings(db, task_id, findings, project_root=...)`**：
   - 把 Orchestrator 输出的 `findings` 写入 `agent_findings` 表
   - 把 §4 的 `dropped_findings` / `unclear_findings` 也一并落库，用 `finding_metadata` 打分区标签
   - 再做一次文件路径存在性验证（过滤 LLM 幻觉）
   - 抽 `EvidenceChain` 存进 `finding_metadata`
2. **统计与打分**：累加所有子 Agent 的 iterations / tool_calls / tokens_used，统计 critical/high/... 计数，算 `security_score`
3. **状态收尾**：`task.status = COMPLETED`，`current_phase = REPORTING`，`completed_at = now()`
4. **落 Agent 树**：`finally` 里 `_save_agent_tree` 把 `agent_registry` 里的运行时 Agent 树落到 `agent_tree_nodes`，方便前端画组织架构图

### 5.1 报告不是主流程产物

**运行期没有"写报告文件"这一步**。真正的报告导出是**前端主动拉取时才拼装**：

- `GET /api/v1/agent-tasks/{task_id}/report?format=markdown` → `generate_audit_report`
- 从 DB 读 `agent_findings`，按 refinement verdict 切成 **active / dropped / unclear** 三区，按严重度排序，拼成 Markdown
- 文件名格式：`audit_report_{task.id[:8]}_YYYYMMDD.md`
- 也支持 `format=json` 直接返 JSON

Verification 阶段的 `create_vulnerability_report` 工具只是产出**单条漏洞的结构化描述**，不是终版报告。

## 6. 实时可视化：SSE 事件流

前端的"审计流日志页"能实时看到每个 Agent 的思考、工具调用、发现，靠的是两条 SSE：

| 接口 | 处理函数 | 特点 |
|---|---|---|
| `GET /agent-tasks/{id}/events` | `stream_agent_events` | 从 DB `agent_events` 表按 sequence 轮询（0.5s），简单可靠 |
| `GET /agent-tasks/{id}/stream` | `stream_agent_with_thinking` | 优先从内存 queue `event_manager.stream_events(...)` 拉，能拿到 **thinking_token 逐 token**；任务已结束/不在跑时回退 DB 轮询（2s，含心跳） |

**事件生产端**：所有阶段的 `AgentEventEmitter.emit_*`（`emit_info / emit_warning / emit_phase_start / emit_finding / emit_llm_thought / emit_task_complete / emit_error`）会双写——push 到内存 queue（给 `/stream`）+ 异步落到 `agent_events` 表（给 `/events` 和回退路径）。

## 7. 状态机小抄

`AgentTask.status`（顶层生命周期，粗粒度）：

```
PENDING  ──create──▶  RUNNING  ──complete──▶  COMPLETED
                       │
                       ├──cancel──▶  CANCELLED
                       └──error ──▶  FAILED
```

`AgentTask.current_phase`（阶段进度，细粒度）：

```
PLANNING  ──▶  RECONNAISSANCE  ──▶  ANALYSIS  ──▶  REPORTING
   (准备)         (Preflight)       (Orchestrator +      (落库 + 报告懒生成)
                                      四个子 Agent)
```

> 注意：`docs/AGENT_AUDIT_ARCHITECTURE.md` 里可能出现 `INDEXING / ANALYZING / VERIFYING` 的字眼，那些是**事件流描述**（`emit_phase_start("preparation")` / `emit_phase_start("orchestration")`），不是 `AgentTaskStatus` 枚举实值。真实枚举只有上面四个粗粒度状态 + 四个细粒度 phase。

## 9. 一句话记住每个 Agent

| Agent | 一句话 | 迭代模式 | 上限 | LLM 调用次数 |
|---|---|---|---|---|
| **Preflight** | 跑 SCA/Secrets/SAST 三大确定性工具，把已知漏洞先摆到台面 | 无 LLM | 一次 | 0 |
| **Orchestrator** | 大脑，每轮问 LLM"接下来派谁" | ReAct | 20 轮 | 每轮 1 次 |
| **Recon** | 摸清项目结构、技术栈、入口点、高风险区 | ReAct | 15 轮 | 每轮 1 次 |
| **Analysis** | 深入代码找漏洞，输出带证据的 findings | ReAct | 30 轮 | 每轮 1 次 |
| **Refinement** | 精修过滤：升格 / 丢弃 / 挂起低置信度 finding | 一次判决，无 ReAct | 1 轮 | **每条 finding 1 次** |
| **Verification** | 起沙箱跑 PoC，判定真伪并附证据链 | ReAct | 25 轮 | 每轮 1 次 |
