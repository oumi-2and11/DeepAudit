## 1. 项目定位与设计原则

### 1.1 一句话定位

**一个基于多智能体协作、以"可验证 + 可复现"为一等公民的开源项目自动安全审计系统。**

- **可审计**：每一次 Agent 决策（用了哪个工具、看了哪段代码、得出什么结论）都写入不可变事件日志，可回放。
- **可验证**：三级验证漏斗（静态污点 → 语义交叉投票 → 沙箱动态 PoC），只有三级都过才标记 `CONFIRMED`。
- **可复现**：每个 `CONFIRMED` 漏洞输出一个 **Reproducibility Kit**——Dockerfile + 代码切片 + PoC + 一键 replay 脚本，评委 30 秒能在自己机器上复现。

### 1.2 vs DeepAudit / AgentStalker / OpenSecurity 的差异化

| 维度 | DeepAudit | AgentStalker | 我们（AuditForge） |
| --- | --- | --- | --- |
| 编排范式 | 自由 Agent 协作 | 静态建模+攻击图 | **确定性流水线 + 事件溯源** |
| 工具协议 | 硬编码 Python 函数 | 内置工具 | **MCP 标准协议**（可插拔） |
| 验证机制 | 单沙箱 PoC | 沙箱动态验证 | **三级漏斗**：静态污点 + 双模型交叉投票 + 沙箱 |
| 证据形态 | JSON 字段 | 证据裁决 | **结构化 EvidenceGraph**（图数据结构 + 可视化） |
| 复现性 | 报告 + 数据 | 无强调 | **Reproducibility Kit**（一键 replay） |
| 误报控制 | 单模型 + LLM 二次判定 | 攻击图剪枝 | **双模型交叉投票 + 静态锚点必须命中** |

> 上表将作为实验报告 §4.5「关键实验技术」的核心对比表。

### 1.3 设计原则（Trade-off 已做）

1. **能用现成的绝不自研**：LangGraph 做编排、Semgrep 做静态、Docker SDK 做沙箱、SQLite 做存储、React 做前端。
2. **确定性优先于智能**：Agent 只在"该调哪个工具、该看哪段代码"处做决策；判定环节走结构化规则+投票，不让 LLM 单点决定。
3. **证据 > 结论**：宁可漏一个真阳性，也不放一个无证据的报警。评价指标里我们主动降低 recall 换 precision。
4. **11 天能做完**：所有 Nice-to-have 进 §12 未来工作，不进 MVP。

### 2.2 五个 Agent 及其职责

| Agent | 输入 | 输出 | 用到的 MCP 工具 |
| --- | --- | --- | --- |
| **Orchestrator** | 用户任务 | 流水线状态 + 最终报告 | — |
| **Recon Agent** | 仓库 URL / 本地路径 | 语言识别、依赖清单、攻击面清单（entry points） | `repo_parser`, `dep_extractor` |
| **Scanner Agent** | 攻击面清单 | 疑似漏洞候选（Finding） | `semgrep`, `gitleaks`, `taint_trace`, `code_read`, `llm_judge` |
| **Verifier Agent** | Finding | Finding + verdict(REJECTED/LIKELY/CONFIRMED) | `llm_judge`(双模型), `code_read`, `sandbox_exec` |
| **Exploiter Agent** | verdict=LIKELY 的 Finding | PoC 脚本 + 沙箱执行结果 + EvidenceGraph | `sandbox_exec`, `llm_judge` |

> **注意：Verifier ≠ Exploiter**。Verifier 做静态+语义判定，Exploiter 做动态 PoC 生成与执行。分开是为了让"过滤误报"和"生成 PoC"两个失败模式解耦。

## 3. 核心工作流：三级验证漏斗

一个候选漏洞从产生到 `CONFIRMED` 要经过三关，任何一关不过就降级或丢弃。

```
[Scanner 产出候选]
       │
       ▼
┌──────────────────────┐
│ L1: 静态锚点验证       │  必须命中一条 Semgrep/Taint 规则，否则丢弃
│  · semgrep 规则命中?  │
│  · 污点路径存在?      │
└──────────┬───────────┘
           │ pass
           ▼
┌──────────────────────┐
│ L2: 语义双模型交叉投票 │  DeepSeek + 通义千问 独立判定，两个都说"真"才进 L3
│  · Model A judge     │
│  · Model B judge     │
│  · 结论一致?          │
└──────────┬───────────┘
           │ both="real"                  │ 一致="false"     │ 不一致
           ▼                              ▼                  ▼
┌──────────────────────┐              [REJECTED]        [LIKELY, 不进 L3]
│ L3: 沙箱动态 PoC      │
│  · Exploiter 生成 PoC │
│  · Docker 执行        │
│  · 观察到 exploit 效果?│
└──────────┬───────────┘
           │ yes                 │ no
           ▼                     ▼
     [CONFIRMED]             [LIKELY, PoC 附上失败日志]
```

**为什么这么设计：**
- L1 保底：LLM 单点错误的兜底，静态规则命中意味着代码里真有可疑模式，不是 LLM 幻觉。
- L2 交叉：两个不同厂商的 LLM 独立判，避免单模型偏见（同厂商 API 不算独立）。
- L3 决定性：动态 PoC 能跑通 = 真漏洞，不能反驳。

**评价指标暴露给报告：** `CONFIRMED` 数、`LIKELY` 数、`REJECTED` 数、L2 一致率、L3 通过率、每个 CONFIRMED 的 Token 消耗。

## 4. 数据模型（SQLite Schema）

### 4.1 核心表

```sql
-- 一次扫描任务
CREATE TABLE scan (
    id              TEXT PRIMARY KEY,   -- ULID
    repo_url        TEXT,
    local_path      TEXT,
    lang            TEXT,               -- 主语言
    status          TEXT,               -- pending/running/done/failed
    started_at      TEXT,
    finished_at     TEXT,
    total_tokens    INTEGER DEFAULT 0,
    total_cost_usd  REAL DEFAULT 0
);

-- 攻击面（Recon 输出）
CREATE TABLE entrypoint (
    id          TEXT PRIMARY KEY,
    scan_id     TEXT REFERENCES scan(id),
    file_path   TEXT,
    kind        TEXT,   -- http_route / cli_arg / rpc / event_handler
    signature   TEXT    -- e.g. "GET /api/user/:id"
);

-- 漏洞候选（Scanner 产出，Verifier 更新 verdict）
CREATE TABLE finding (
    id              TEXT PRIMARY KEY,
    scan_id         TEXT REFERENCES scan(id),
    cwe             TEXT,      -- CWE-89 / CWE-78 / ...
    kind            TEXT,      -- sqli / cmdi / path_traversal / hardcoded_secret / xss / ssrf / xxe / deserialization
    severity        TEXT,      -- critical/high/medium/low
    file_path       TEXT,
    line_start      INTEGER,
    line_end        INTEGER,
    source_snippet  TEXT,
    sink_snippet    TEXT,
    l1_static_hit   INTEGER,   -- 0/1
    l2_verdict      TEXT,      -- pending/real/false/split
    l2_votes        TEXT,      -- JSON: {"deepseek":"real","qwen":"false"}
    l3_verdict      TEXT,      -- pending/confirmed/failed/skipped
    final_verdict   TEXT,      -- CONFIRMED/LIKELY/REJECTED
    created_at      TEXT
);

-- 证据链（一个 finding 一个证据图）
CREATE TABLE evidence (
    finding_id      TEXT PRIMARY KEY REFERENCES finding(id),
    call_graph_json TEXT,           -- 节点=函数, 边=调用, JSON
    taint_path_json TEXT,           -- source→...→sink 的路径
    poc_script      TEXT,           -- PoC 源码
    poc_lang        TEXT,           -- python/bash/curl
    sandbox_stdout  TEXT,
    sandbox_stderr  TEXT,
    sandbox_exit    INTEGER,
    reproduce_kit_path TEXT         -- zip 路径
);

-- 事件溯源日志（追加写入，永不修改）
CREATE TABLE audit_event (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    scan_id     TEXT REFERENCES scan(id),
    ts          TEXT,        -- ISO 8601
    actor       TEXT,        -- orchestrator/recon/scanner/verifier/exploiter
    action      TEXT,        -- tool_call / decision / verdict / error
    payload     TEXT         -- JSON, 完整可 replay
);
```

## 5. MCP 工具层

选题明确要求 MCP，我们把所有工具封装成 MCP Server，Agent 用标准 MCP Client 调用。这也让工具能被别的项目（比如 DeepAudit）复用，作为对比实验的额外证据。

### 5.1 工具清单

| MCP 工具 | 输入 | 输出 | 实现依赖 |
| --- | --- | --- | --- |
| `repo_parser` | 仓库路径 | `{lang, files[], deps[], loc}` | `tree-sitter`, `enry` |
| `dep_extractor` | 语言 + 项目路径 | 依赖列表 + 已知 CVE | `pip-audit`, `npm audit`, `osv-scanner` |
| `semgrep` | 路径 + 规则集 | Finding 列表 | `semgrep` pip 包 |
| `taint_trace` | 文件 + 起点 | 数据流路径 | `tree-sitter` + 自研简易 taint 引擎 |
| `code_read` | 文件 + 行号范围 | 代码文本 + 上下文 | 文件系统 |
| `gitleaks` | 路径 | 硬编码密钥列表 | `gitleaks` 二进制 |
| `llm_judge` | prompt + 上下文 | verdict + reason + confidence | LiteLLM（多 provider） |
| `sandbox_exec` | 语言 + 脚本 + 目标代码 | stdout/stderr/exit | Docker Python SDK |
| `reproduce_kit_build` | Finding | zip 路径 | 内部脚本 |

### 5.2 MCP Server 结构

```
mcp_tools/
├── server.py              # 一个进程一个工具或多工具聚合
├── schemas/               # 每个工具的 JSON Schema
│   ├── semgrep.json
│   ├── taint_trace.json
│   └── ...
└── impl/
    ├── semgrep_tool.py
    ├── taint_tool.py
    ├── sandbox_tool.py
    └── ...
```

Agent 侧统一走 `mcp.client`，工具替换 → 只改 MCP Server，Agent 代码零改动。

## 6. 关键模块详细设计

### 6.1 Recon Agent

**目标**：从 Scanner 视角回答"这个仓库我该扫哪些地方"。

流程：
1. 调 `repo_parser` → 拿到语言 + 文件树。
2. 按语言分派：
   - Python (Flask/FastAPI/Django) → grep `@app.route`, `@router.get` 等 → 生成 `http_route` entrypoints。
   - Node.js (Express/Koa) → grep `app.get`, `router.post`。
   - Go → grep `http.HandleFunc`, `gin.Default().GET`。
   - PHP → grep `$_GET`, `$_POST`, `$_REQUEST` 首次出现的函数。
3. 调 `dep_extractor` → 拿到依赖 + 已知 CVE 清单（这块直接影响 Scanner 的优先级排序）。
4. 输出 `entrypoint` 表。

**决策点**：Recon 不做深度语义分析，纯规则+关键字，快。深度理解交给 Scanner。

### 6.2 Scanner Agent

**输入**：entrypoints。
**输出**：Finding 候选（可能有误报）。

流程（对每个 entrypoint）：
1. 调 `semgrep` 跑通用规则集（我们从 Semgrep Registry 挑 SQL/CMDI/Path/Deserialization 等相关规则）。
2. 对 semgrep 命中的位置，调 `taint_trace` 反向找 source。
3. 拿到 (source, sink, path) 三元组后，调 `llm_judge` 让 LLM 补充语义判断（比如：这是不是自封装的安全函数、有没有 sanitizer）。
4. 输出 Finding，标 `l1_static_hit=1`。

**决策点**：**Scanner 不做否决**。LLM 说"不像"也要写入 Finding，交给 Verifier 处理。这是"疑罪不从有"的对偶——先记录再筛选，避免早期 Agent 一票否决导致漏报。

### 6.3 Verifier Agent（去误报核心）

**输入**：Finding。
**输出**：Finding + `l2_verdict`。

流程：
1. 从 Finding 拿到 source/sink/path，调 `code_read` 加载完整上下文（前后 20 行 + 相关辅助函数）。
2. 构造两个 prompt 完全相同的 `llm_judge` 请求，分别路由到 **DeepSeek** 和 **通义千问**（不同厂商 → 独立性）。
3. 两个模型各自输出 `{verdict, confidence, reason}`。
4. 合成：
   - 两个都 `real` → `l2_verdict=real`，进 Exploiter。
   - 两个都 `false` → `l2_verdict=false`，final=`REJECTED`。
   - 一 `real` 一 `false` → `l2_verdict=split`，final=`LIKELY`，不进 L3（避免浪费沙箱资源）。

**决策点**：为什么不用三模型多数投票？成本 vs 收益不划算，双模型已经能显著降误报（消融实验会验证）。

### 6.4 Exploiter Agent

**输入**：`l2_verdict=real` 的 Finding。
**输出**：PoC + 沙箱执行结果 + EvidenceGraph。

流程：
1. 从 EvidenceGraph 提取 source 类型（http_param / cli_arg / file_read / ...）。
2. 让 LLM 按模板生成 PoC（我们内置 8 种漏洞类型 × 3 种触发方式的 PoC 模板）：
   - SQLi → curl + `' OR '1'='1` 或时间盲注
   - CMDi → curl + `;id` / `` `id` ``
   - Path Traversal → curl + `../../etc/passwd`
   - Hardcoded Secret → 直接把凭证拿去尝试连服务
   - Deserialization → 生成 payload 二进制
3. 调 `sandbox_exec`：把 PoC 脚本 + 目标代码切片放进沙箱容器，执行，捕获 stdout/stderr/exit。
4. LLM 判定 exploit 是否成功（比如："输出包含数据表内容" 或 "响应返回了 /etc/passwd 前几行"）。
5. 成功 → `final_verdict=CONFIRMED`，调 `reproduce_kit_build` 打包。
6. 失败 → `final_verdict=LIKELY`，附上失败日志（说不定是环境问题，不是漏洞不存在）。

**决策点**：**Exploiter 有 3 次重试**，每次失败后把上一次的 stderr 反馈给 LLM 让它修正 PoC。3 次都失败才降级。这是从 DeepAudit 学的。

### 6.5 事件溯源（Event Sourcing）

每个 Agent 每次动作、每次工具调用、每次决策，都通过统一的 `EventBus.emit()` 写入 `audit_event` 表。

事件类型：
```
tool_call.request     { agent, tool, input_hash }
tool_call.response    { agent, tool, output_hash, duration_ms }
agent.decision        { agent, decision, alternatives, reason }
agent.verdict         { agent, finding_id, verdict, confidence }
error                 { agent, error_type, message, stack }
```

**用途**：
- 报告生成时，可以从事件流恢复出完整的审计过程。
- 前端"审计流日志"页面 SSE 实时推事件。
- Replay：给定同一个 repo + 同一个事件流，能重建所有 Finding（缓存 LLM 响应）。

## 7. 复现性套件（Reproducibility Kit）

**这是我们相对 DeepAudit 的杀手锏**，也是评委答辩时最好演示的点。

每个 `CONFIRMED` 漏洞输出一个 zip：

```
CVE-candidate-xxxx.zip
├── README.md              # 3 步复现说明
├── Dockerfile             # 基于 alpine，装最小依赖
├── vulnerable_code/       # 从原仓库切出来的最小可复现代码
│   ├── app.py
│   └── requirements.txt
├── poc.sh                 # 一键触发脚本
├── expected_output.txt    # 预期 exploit 结果
└── evidence.json          # EvidenceGraph 完整 JSON
```

评委在自己机器上：
```bash
unzip CVE-candidate-xxxx.zip && cd CVE-candidate-xxxx
docker build -t poc . && docker run --rm -it poc bash poc.sh
# 30 秒内看到 exploit 输出
```

这一段可以直接写进答辩 PPT 演示流程。

## 8. 报告生成

### 8.1 报告结构（Markdown / HTML / PDF 三种）

```
# 审计报告 - <project_name>

## 1. 摘要
- 扫描时间、总耗时、Token 消耗、总费用
- CONFIRMED / LIKELY / REJECTED 统计

## 2. 项目画像
- 语言分布 / LoC / 依赖数 / 已知 CVE 依赖数

## 3. 漏洞列表（按严重性排序）
每个漏洞一个小节：
  - CWE / 类型 / 严重性 / final_verdict
  - 文件位置（可跳转到 GitHub 行级链接）
  - EvidenceGraph 可视化图片（用 mermaid 生成）
  - PoC 代码
  - 沙箱执行输出
  - 修复建议（LLM 生成）
  - 下载 Reproducibility Kit 链接

## 4. 附录
  - 完整事件日志（可折叠）
  - Baseline 对比（如果和 DeepAudit 做了对比扫描）
```

### 8.2 前端查看器

极简 React + Vite 单页应用，只做：
- 报告列表页 → 点进去看单个报告。
- 漏洞详情页 → 展示 EvidenceGraph + PoC + 沙箱输出。
- 审计流日志页 → SSE 实时看 Agent 干活。
- 下载 kit 按钮。

**不做**：项目管理、多用户、权限、编辑功能。这些是 DeepAudit 的加分项，但对课程作业是过度设计。

## 10. 技术栈定稿

| 层 | 选型 | 理由 |
| --- | --- | --- |
| Agent 编排 | **LangGraph** | 状态机式，天然适合我们的确定性流水线 |
| LLM 调用 | **LiteLLM** | 一套 API 覆盖 DeepSeek/Qwen/OpenAI，切换零成本 |
| Web 框架 | **FastAPI** | 自带 SSE、Swagger、异步 |
| ORM / DB | **SQLAlchemy + SQLite** | 单文件、零运维；量不大不需要 Postgres |
| MCP | **官方 `mcp` Python SDK** | 直接符合选题要求 |
| 静态分析 | **Semgrep**（PyPI 包） | 规则丰富、多语言 |
| 语法解析 | **tree-sitter** | 做 taint_trace |
| 沙箱 | **Docker Python SDK** + 复用 DeepAudit 的 sandbox 镜像 | 省事，还能对比 |
| 密钥扫描 | **gitleaks** | 单文件二进制 |
| 依赖 CVE | **osv-scanner** | Google 出品，覆盖多语言 |
| 前端 | **Vite + React + shadcn/ui** | 极简够用 |
| 报告 PDF | **WeasyPrint** | Python 生态最省心 |
| 图可视化 | **mermaid** | md 里直接嵌 |
| 包管理 | **uv** (Python) + **pnpm** (JS) | 快 |
| 部署 | **docker compose** | 一致性 |
